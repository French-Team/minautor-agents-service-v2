exemple de structure dans le vivier :

- entrée du vivier
	- theme 'question/reponse' (permettra par la suite de les injecter par le pilote)
		- theme de question sur le vivier
		- theme de question par sujet / categorie / action   
	- theme par 'type de fichier' (permet de se diriger directement vers un type de fichier)
		- theme '.html'
			- theme 'boite a outil html'
				- creer un fichier
				- modifier un fichier
					- chercher dans le fichier
						- elements
							- head
							- import
							- etc
				- analyser le fichier
					- analyseur 1
					- analyseur 2
				- valider & certifier le fichier
		- theme '.css'
			- theme 'boite a outil css'
				- creer un fichier
				- modifier un fichier
					- chercher dans le fichier
						- elements
							- head
							- import
							- etc
				- analyser le fichier
					- analyseur 1
					- analyseur 2
				- valider & certifier le fichier
	theme par 'framework' (permettra de suivre des themes dedié a chaque framework)
		- theme 'nextJS'
			- rechercher les dernieres innovation du framework
				- mode de recherche A
				- mode de recherche B
				- mode de recherche C
				- mises a jour recentes
			- creer un projet
				- de base
				- avec options pre-installé
					- theme A (configuration minimal)
					- theme B (configuration avec tailwind)
					- theme C (configuration sans tailwind)
il va etre tres important de considerer le vivier comme un pulzze modulaire et evolutf, composer de bloc en liaison avec d'autres blocs 'avant et apres'eux.
mais il va etre important de pouvoir intercaler un bloc entre deux blocs.
par la suite, personne ne viendra lire le vivier, il sera injecter par le pilote, on peut donc se dire que meme si il devient 'complexe', c'est le pilote qui va etre equipé d'automatismes pour gerer l'integralité des themes qui seront dans le vivier. 
nous sommes en 'constante evolution' et il sera normal de devoir verifier l'etat fonctionnel actuel pour l'ameliorer sans le detruire.
